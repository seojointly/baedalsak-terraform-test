인스턴스 사양·확장(HPA·replica) 수치는 "변경 가능" 항목이라 완성 조건에서 제외합니다.

## 1. 앱 파드 설정 — 팀 결정값(CLAUDE.md) vs 검증값(`helm/values/aws.yaml`)

| 항목 | 팀 결정 (baedalsak-infra/CLAUDE.md) | 검증값 (지금 aws.yaml) | 정할 것 |
|---|---|---|---|
| CPU limit | AWS `250m / 1` (limit 1 코어) | requests 250m, **limit 없음** (`cpu: null`) | limit 을 둘지, 둔다면 값 |
| 종료 | preStop **10s**, terminationGracePeriodSeconds **45** | preStop **20s**, grace **60** | 둘 중 무엇으로 |
| startup probe | `/actuator/health/liveness` 5s × **30** (로컬만 × 60) | 5s × **60** | AWS 도 × 60 을 쓸지 |

### CPU limit
- **limit 없음으로 둔 이유**: JVM 은 기동할 때 CPU 를 많이 씀 → limit 이 있으면 CFS 스로틀링으로 기동이 느려져 startup/readiness 가 늦어지거나 실패할 수 있음. requests 만 두면 노드에 여유가 있을 때 더 쓰고, 스케줄링·HPA 는 requests 기준으로 동작.
- **limit 을 두는 이유**: 한 파드가 노드 CPU 를 다 써서 다른 파드(같은 노드의 서비스·애드온)를 굶기는 것을 막음. 팀 결정이 limit 1 인 근거도 이것.
- 선택지
  - A. limit 1 (팀 결정) — startup probe 를 넉넉히(× 60) 두면 기동 지연을 흡수할 수 있음. 적용 후 켜기 1회로 기동 시간 확인 필요
  - B. limit 없음 (검증값) — CLAUDE.md 결정값을 바꿔야 함 (팀 공유 필요)
- HPA 는 CPU **requests** 대비 사용률이라 어느 쪽이든 HPA 동작에는 영향 없음.

### 종료 (preStop · terminationGracePeriodSeconds)
- 순서: 파드 종료 시작 → preStop sleep(그동안 ALB 가 대상 그룹에서 파드를 빼고 새 요청을 안 보냄) → SIGTERM → Spring graceful shutdown → grace 초과 시 강제 종료.
- **AWS 에서 20s 로 늘린 이유**: 대상 그룹 `deregistration_delay` 30s, 헬스체크 10s × 2회 → ALB 가 파드를 빼는 데 10s 보다 오래 걸릴 수 있음. 10s 면 빠지기 전에 SIGTERM 이 와서 롤링 배포 중 502 가 날 수 있음.
- grace 는 `preStop + graceful shutdown 시간 + 여유` 이상이어야 함 (20 + 20 + 20 = 60).
- 로컬(Traefik)은 엔드포인트 반영이 빨라 10s/45 로 충분 → **로컬 10s/45 · AWS 20s/60 처럼 환경별로 다르게 두는 안**도 가능.
- 같이 볼 값: `terraform/ephemeral/alb.tf` 의 `deregistration_delay = 30`, `scripts/aws/deploy.sh` 롤링 설정.

### startup probe
- 검증 때 서비스 6개가 노드 2대에서 동시에 기동 → × 30(최대 150s)이면 일부가 기동 중에 재시작될 위험이 있어 × 60(최대 300s)으로 둠.
- 기동 시간을 재보고(켜기 로그의 Ready 까지 시간) 줄이는 것을 권장. CPU limit 을 두면(A) 기동이 더 느려지므로 × 60 유지가 안전.
